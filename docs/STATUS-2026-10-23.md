## What we found

### 1. The crash was the hook stubs (fixed in 0.1.23)
probe.c's hooks (red orb multiplier, cheats, enemy health bar, damage/orb pickup multipliers) jump from the
game to x86 stubs in their own low-map pages. On iOS `protect(..., 5)` only makes them readable, and they
were never passed to `guest_cpu_code`, so FEXCore's `QueryGuestExecutableRange` reported NOEXEC the first time
a hooked path ran. The 0.1.22 log confirms it: the crash came on a jump (the infinite double jumps cheat hook),
at guest offset 0x2400700, a stub page just before the main stack, in 256-byte stub slot 7. `protect_code`
registers every stub page, and the ISA rewrite stub area after the image too.

### 2. Most of the GPU time was forced MSAA and the oversized surface (0.1.24)
- GoW3 draws with 1 colour sample and 2 depth samples. Metal has no mixed sample counts, so the colour
  targets were forced to 2 samples, and the tile GPU stored 2-sample colour and depth in every pass.
  MoltenVK now takes the single-sampled path that AMD and Intel Windows drivers already use
  (`GOW3_NO_MSAA=0` restores it).
- The game view was 2622x1206 (3x). The game renders at 1066x600, so it is now at most 2x (1748x804).
- Result: 8-12 -> ~27 FPS, and the phone runs cooler.

### 3. Where the remaining frame time goes (logs from 0.1.24 / 0.1.25)
- `GPU ticks` takes 40-55 ms of a 50-66 ms frame. The CPU side (FEX, draw preparation) finishes early and
  waits. **The bottleneck is the GPU running the translated work, not FEXCore.**
- MoltenVK: encoding Vulkan into Metal costs ~1 ms per command buffer, executing on the GPU 40-60 ms, and the
  present waits ~33 ms on that.
- The 150-460 ms spikes are first-visit shader compiles (MSL compile up to 2.2 s, pipeline compile up to
  1.6 s). They are cached for the next visit.
- 400-4000 draws per frame. Which passes cost the most is not known yet (see next move 3).

### 4. The texture corruption: what it is not
| Test | Result |
|---|---|
| `GOW3_BUFFER_BOUNDS=1` (0.1.22 shader bounds checks) | no change, Kratos invisible: off by default since 0.1.23 |
| `GOW3_NO_MSAA=0` (MSAA back on) | right for a while, then broken again (FPS rose when it broke) |
| `toggles-all-off` / `tracking` / `none` (0.1.25 `toggles.txt`) | broken in all three: not the texture caches, page tracking shortcuts or the threaded draw pipeline |
| `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS=0` | still broken, and 16 FPS instead of 27: not argument buffers |
| MoltenVK fast math off (0.1.20) | no change |

So the fault is below the port's own optimizations, in the Vulkan-to-Metal layer.

### 5. Prime suspect: push descriptors on MoltenVK 1.4.1+ (change in 0.1.27, untested)
KytyPS5 (a PS5 emulator, PR #1083) found that MoltenVK 1.4.1 and later leave **buffer-size metadata stale for
pushed descriptors**, which corrupted their rendering. Their fix was regular descriptor sets on those
versions. This matches us:
- The app ships MoltenVK 1.4.2 (`native/scripts/build-ios.sh`).
- shadPS4 pushes the descriptors of nearly every draw and dispatch (`vk_pipeline_common.cpp`).
- The 0.1.22 bounds checks read exactly that metadata (`OpArrayLength`) and made Kratos disappear.
- None of the tests above touch push descriptors, which explains why they all failed.

0.1.27: `Instance::MaxPushDescriptors` returns 0 on MoltenVK >= 1.4.1, so graphics and compute pipelines use
their existing descriptor set path (the pool rotates and grows, all on the GPU thread). The log prints
`GPU: push descriptors off ...`. `GOW3_PUSH_DESCRIPTORS=1` turns them back on; the shader binary cache gets its
own salt (16). Not compiled locally (no Boost on this machine): check gpu.yml or the IPA build first.

### 6. Alternatives to MoltenVK (checked Oct 2026)
- **KosmicKrisp** (Mesa / LunarG, Vulkan on Metal 4): Vulkan 1.4 conformant on macOS 26 and close to native
  Metal speed, but **no iOS support** (LunarG lacks the staffing and CI for it). It would be the drop-in
  successor once iOS lands; shadPS4 already has KosmicKrisp workarounds (`eMesaKosmickrisp`).
- A native Metal backend for the shadPS4 video core: months of work, not now.
- DXMT (Madeira) is D3D11 -> Metal and does not apply.
- MoltenVK 1.4.3 (unreleased) lists no push descriptor fix.

## Tools added for testing on the phone (no PC needed)
| File in `Documents/gow3/` | Effect |
|---|---|
| `env.txt` | `KEY=VALUE` environment for the next start (0.1.20) |
| `toggles.txt` | number whose bits switch GPU/memory optimizations off, re-read every 250 ms (0.1.25); masks in `docs/toggles/` |
| `capture.txt` | records the next frame's passes, targets, formats and shaders to `gow3/user/captures/frame_*.txt`, then is deleted (0.1.26) |
| `GOW3_GPU_PROFILE=2` in env.txt | GPU ms per pass on MoltenVK: one submission per timestamp (0.1.24); slower while on |

Normal `env.txt`:
```
FEX_DISABLEL2CACHE=0
FEX_DYNAMICL1CACHE=0
MVK_CONFIG_PERFORMANCE_TRACKING=1
MVK_CONFIG_PERFORMANCE_LOGGING_FRAME_COUNT=300
```

## Next moves, in order
1. **0.1.27 on the device:** go where the textures were broken. Confirm `GPU: push descriptors off` in the log.
   - If fixed: compare FPS with 0.1.24 (descriptor set updates cost some CPU), then compare against
     `GOW3_PUSH_DESCRIPTORS=1` once to be sure.
   - If still broken: step 2.
2. **Frame capture of a broken scene** (`capture.txt`) plus a screenshot, and every `[mvk-error]` / `[mvk-warn]`
   line in the log: formats the A19 cannot do and shader translation failures show there.
3. **GPU profile** (`GOW3_GPU_PROFILE=2`, 30 s in a slow scene): `GPU profile:` lines give ms per pass. Fix the
   top passes (load/store churn, format fallbacks, slow compute) toward 30-35+ FPS.
4. **Pacing:** present at 120 Hz (ProMotion) or offer a 30 FPS lock; then heat tuning (thermal-state
   adaptation, frame cap).
5. **The 64-write-fault safety net** (probe.c, 0.1.17) fires repeatedly at one address (`0x73b9a02828`) and leaves
   the page untracked each time: find what lives there and track it properly.
6. Later: on-screen touch controls (one native build for an RN overlay plus `setVirtualPad`; JS-only updates
   after that), save backup in the app, boot.bin preparation on the phone.
